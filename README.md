# Cinema API — Java Spring, API First

Этот API нужен, чтобы показывать афишу и расписание кинотеатра, выбирать места, бронировать их и покупать билеты.

Репозиторий: https://github.com/denissotnikov4/APIFirstSber

В корне находятся `api.yaml` (OpenAPI 3.0.3), настройки кодогенератора и README; в `service/` — сгенерированные контракты и Spring Boot каркас. Java 21, Spring Boot 3.5.16, Springdoc 2.10.0, OpenAPI Generator 7.12.0. Версии зафиксированы; сочетание Boot 3.5 / Springdoc 2.x выбрано по [матрице совместимости](https://springdoc.org/v2/#what-is-the-compatibility-matrix-of-springdoc-openapi-with-spring-boot).

## Контракт: пять операций

| Метод | Путь | Назначение | Успешный ответ |
|---|---|---|---|
| GET | `/api/v1/movies?date=2026-11-15&page=0&size=20` | Афиша с расписанием | `200`, страница фильмов |
| GET | `/api/v1/sessions/{sessionId}` | Один сеанс со схемой зала | `200`, сеанс и места |
| POST | `/api/v1/reservations` | Создание брони на 15 минут | `201` + `Location`; `200` при повторе |
| PATCH | `/api/v1/reservations/{reservationId}` | Изменение состояния брони после оплаты | `200`, бронь с билетами |
| DELETE | `/api/v1/reservations/{reservationId}` | Отмена неоплаченной брони | `200`, результат отмены |

У каждой операции есть `summary`, параметры, ответ `200` и ошибки с причинами. Сохранили пять операций и четыре различных HTTP-метода из задания. Расписание вложено в афишу, схема зала — в сеанс.

REST-решения:

- URI обозначают ресурсы во множественном числе. `/api/v1` — выбранная стратегия версионирования, а не требование REST.
- POST создаёт ресурс и возвращает `201 Created` с URI в `Location`. `200` используется для повторного запроса с тем же ключом и содержимым. Отдельный GET брони не добавлен из-за ограничения пяти операций: по URI доступны PATCH и DELETE, представление возвращается в ответах на изменения.
- PATCH меняет часть состояния брони. Это JSON по схеме `UpdateReservationDto`, не JSON Patch: `{"status":"PAID","paymentReference":"pay_123"}`. Сервер обязан проверить оплату, прежде чем принять состояние. PUT для частичного изменения больше не используется.
- DELETE возвращает `200` с представлением результата отмены; это допустимая альтернатива `204` и сохраняет требование задания. Для повторной отмены — тот же результат, для оплаченной/истёкшей брони — `409`.
- Идемпотентность POST обеспечивается контрактом заголовка `Idempotency-Key`: область ключа — пользователь, срок — 24 часа, изменённое содержимое — `409`. Порядок `seatIds` несущественен. Повтор не продлевает бронь. PATCH с тем же подтверждением оплаты также не должен повторно выпускать билеты.
- Пагинация ограничена 100 фильмами. Порядок фиксирован: фильмы по `title, id`, сеансы по `startsAt, id`. За границей выборки возвращается пустой список.
- Дата афиши относится к `Asia/Yekaterinburg`; время содержит смещение UTC. Суммы — целые копейки RUB. Координаты схемы зала задаются рядом от экрана и номером места; пропуски обозначают проходы.

Семантика методов и ответов: [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [PATCH — RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html).

## DTO, ошибки и безопасность

DTO объявлены в `components/schemas` и генерируются в `ru.cinema.dto`. Входные `CreateReservationDto` и `UpdateReservationDto` отделены от выходных моделей. Внешний контракт не содержит сущностей БД, владельца брони, внутренних блокировок и карточных данных. Владелец определяется из проверенного JWT `sub`, цена — сервером.

Ошибки имеют тип `application/problem+json` по [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html):

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Request parameters or body are invalid.",
  "instance": "/api/v1/reservations",
  "code": "INVALID_REQUEST",
  "errors": [{"field": "seatIds", "message": "size must be between 1 and 10"}]
}
```

`400` — некорректный ввод; `401` — нет действительного JWT («не знаю, кто ты»); `403` — недостаточно прав («знаю, но нельзя»); `404` — ресурс отсутствует; `409` — конфликт мест/состояния/ключа/оплаты. Для непредвиденных ошибок предусмотрен `500`, для ещё не реализованных операций каркаса — `501`. HTTP-слой также обрабатывает стандартные `405`, `406`, `415`.

Единый `@RestControllerAdvice` использует Spring `ProblemDetail`; тот же формат используют обработчики Spring Security. В ответах нет SQL, stack trace, исходных сообщений исключений, отклонённых значений и секретов. Причины валидации возвращаются отдельно от значений. [Механизм ошибок Spring](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html).

Реально реализовано в каркасе:

- Bean Validation из контракта: обязательные поля, UUID, дата, диапазоны пагинации, размер списка и формат подтверждения оплаты.
- Строгий JSON: неизвестные поля, повторяющиеся ключи и числовые значения enum запрещены. Специальный Jackson mixin отклоняет повторные и `null`-места: стандартный сгенерированный `Set` иначе молча удалил бы дубликаты до валидации.
- Spring Security OAuth2 Resource Server: JWT-подпись RS256, issuer, audience, срок действия и `nbf`, обязательные `exp` и непустой `sub`. Сеансы HTTP не создаются; аутентификация только через `Authorization: Bearer`, без cookie/form login/basic auth. CSRF отключён именно для этого режима.
- Публичны GET каталога и Swagger; изменения требуют JWT. Ответ `401` содержит `WWW-Authenticate: Bearer`. Стандартные заголовки Spring Security запрещают кеширование ответов (`no-store`).

Для своего провайдера задайте **все три** переменные `JWT_ISSUER`, `JWT_JWK_SET_URI`, `JWT_AUDIENCE`. В рабочей среде issuer/JWKS должны использовать HTTPS. Без настройки провайдера приложение запускается для просмотра каталога/документации, но отклоняет все bearer-токены. Частичная настройка останавливает запуск. Тесты используют временные RSA-ключи и локальный JWKS-сервер; ключи и токены в проект не сохраняются.

## Архитектура и границы задания

```text
api.yaml → OpenAPI Generator → api/, dto/
                                 ↓
HTTP → security/ → web/ → application/
```

`api/` и `dto/` генерируются. `web/` содержит тонкие контроллеры с обязательной передачей делегатов через конструктор, обработчик ошибок и JSON-настройки. `application/` содержит явно названные заглушки `CatalogStub` и `ReservationsStub`. `security/` отвечает за проверку JWT.

**Это каркас по исходному заданию, не готовая касса.** Корректный запрос, прошедший безопасность и валидацию, возвращает документированный `501` в формате Problem Details. Для бизнес-реализации нужно заменить заглушки реализациями сгенерированных делегатов; DTO и интерфейсы вручную менять не требуется.

БД, проверка владельца брони (доменный `403`), проверка платежа у провайдера, хранилище ключей идемпотентности, освобождение истёкших броней и атомарная продажа мест пока описаны **контрактом**, но не реализованы. При добавлении БД эти операции требуют транзакций и ограничения уникальности занятости `(session_id, seat_id)`; один `@Transactional` без защиты конкурентной записи недостаточен. Возврат оплаченных билетов и выдача JWT находятся вне API.

## Генерация, сборка и запуск

Требуются JDK 21 и Maven 3.9+. Из корня, PowerShell:

```powershell
New-Item -ItemType Directory -Force .tools | Out-Null
curl.exe -fL https://repo.maven.apache.org/maven2/org/openapitools/openapi-generator-cli/7.12.0/openapi-generator-cli-7.12.0.jar -o .tools/openapi-generator-cli-7.12.0.jar
./scripts/generate.ps1
mvn -f service/pom.xml clean verify
mvn -f service/pom.xml spring-boot:run
```

Скрипт проверяет версию CLI и спецификацию, удаляет только перечисленные в манифесте сгенерированные API/DTO с маркером генератора и повторяет:

```shell
openapi-generator-cli validate -i api.yaml
openapi-generator-cli generate -i api.yaml -g spring -o service -c generator-config.yaml
```

Используется официальный JAR того же CLI. `.openapi-generator-ignore` защищает поддерживаемые вручную POM, стартовый класс, настройки и README, а также исключает стандартные контроллеры с необязательными зависимостями — адаптеры находятся в `web/`. Скрипт нужен в том числе для удаления устаревших DTO при переименовании. Не удаляйте весь `service/`: там есть и сгенерированный, и рукописный код.

API: http://localhost:8080/api/v1/movies?date=2026-11-15

Swagger UI: http://localhost:8080/swagger-ui/index.html

Springdoc OpenAPI: http://localhost:8080/v3/api-docs

Исходную спецификацию также можно загрузить в [Swagger Editor](https://editor.swagger.io/). Документация [CLI](https://openapi-generator.tech/docs/installation/) и [генератора Spring](https://openapi-generator.tech/docs/generators/spring/).

## Как делали

Итоговые пользовательские промпты приведены ниже в отредактированной форме: это не дословная история переписки, а структурированные формулировки исходных задач с уточнёнными критериями качества.

**Промпт 1. Проектирование контракта и генерация Spring-сервиса**

> Разработай учебный проект Cinema API на Java Spring Boot, используя подход API First: сначала опиши внешний контракт, затем сгенерируй по нему каркас сервиса.
>
> Предметная область — кинотеатр. Контракт должен охватывать афишу фильмов, расписание сеансов, схему зала с доступностью мест, бронирование и покупку билетов, а также отмену неоплаченной брони.
>
> Создай в корне репозитория `api.yaml` в формате OpenAPI 3.0. Предусмотри ровно пять операций: GET списка, GET одного ресурса, POST создания, PUT или PATCH изменения и DELETE удаления либо отмены. Для каждой операции укажи `operationId`, `summary`, параметры с ограничениями, тело запроса при необходимости, успешные ответы и ошибки с конкретными причинами. Сохрани требование задания: у каждой операции должен быть описан ответ `200`. Объясни различия между `401`, `403` и `404` в контексте выбранных сценариев.
>
> Определи DTO в `components/schemas`. Отдели входные модели от выходных, не раскрывай сущности хранения и внутренние служебные данные. Явно опиши правила расчёта стоимости, срок действия брони, конфликты занятости мест и поведение при повторных запросах.
>
> Выполни проверку спецификации и реальную генерацию через OpenAPI Generator CLI с генератором `spring`, разместив результат в `service/`. Зафиксируй версию инструмента и настройки, необходимые для воспроизведения генерации. Проверь компиляцию и загрузку Spring-контекста.
>
> Подготовь README: назначение API одной фразой, принятые проектные решения, команды генерации, сборки и запуска, сведения об использовании агента и модели, итоговые промпты и перечень изменений вне кодогенератора. Явно отдели реализованную инфраструктуру от бизнес-логики, оставленной в виде заглушек.
>
> Критерии приёмки: спецификация валидна; присутствуют все пять операций с требуемыми HTTP-методами; код действительно получен генератором; сервис собирается; результаты проверок и ограничения отражены в README.

**Промпт 2. Доработка контракта и каркаса по практикам REST и Spring**

> Проведи ревью существующего Cinema API и внеси обоснованные улучшения в контракт и Spring Boot каркас. Сохрани предметную область и ограничения исходного задания: пять операций, OpenAPI 3.0, DTO в `components` и воспроизводимая кодогенерация.
>
> Проверь ресурсную модель URI, выбор HTTP-методов и семантику статусов. Используй PATCH для частичного изменения ресурса; для создания предусмотри ответ `201 Created` с `Location`, сохранив осмысленный сценарий ответа `200`, требуемого заданием. Опиши идемпотентность повторов, конфликты состояния, ограничение размера страницы и стабильный порядок выдачи. Объясни компромиссы, обусловленные учебными ограничениями.
>
> Унифицируй ошибки в формате Problem Details по RFC 9457. Реализуй централизованную обработку исключений, валидацию параметров и DTO, отклонение неизвестных полей и некорректных коллекций. Не возвращай клиенту stack trace, внутренние сообщения исключений или чувствительные значения.
>
> Настрой Spring Security для stateless-аутентификации через Bearer JWT: проверку подписи, issuer, audience и временных ограничений токена. Раздели публичные и защищённые операции, обеспечь корректные ответы `401` и `403`. При отсутствии конфигурации провайдера защищённые операции должны оставаться закрытыми. Не храни секреты в репозитории.
>
> Раздели сгенерированные API/DTO и поддерживаемый вручную код. Используй тонкие контроллеры и обязательную передачу зависимостей через конструкторы. Подбери совместимые версии Java, Spring Boot и Springdoc. Обеспечь повторную генерацию без потери ручных доработок и накопления устаревших моделей.
>
> Добавь тесты HTTP-валидации, формата ошибок, правил доступа, проверки JWT и доступности Swagger. Повторно проверь спецификацию, выполни кодогенерацию и Maven-сборку с тестами. Обнови README: опиши изменения, причины решений, порядок настройки и фактические результаты проверок. Сохрани объём задания на уровне каркаса; не представляй ещё не реализованные платежи, транзакции и бронирование как готовую функциональность.

Вне кодогенератора написаны спецификация, настройки и скрипт генерации, README, POM, стартовый класс, контроллеры-адаптеры, обработчики ошибок, конфигурации JSON/JWT, явные заглушки и тесты. DTO и API-интерфейсы получены повторной генерацией, без ручного редактирования.
